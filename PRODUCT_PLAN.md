# Epic-Based Product Plan: Postop Wound Progress Gallery

> **Planning gate:** This document defines product capabilities only. It deliberately does not break epics into implementation milestones or begin implementation. User confirmation of the epic map is required first.

## E0 — Planning and Decisions

### Product brief

| Input | Grounded decision |
| --- | --- |
| App name | **Postop Wound Progress Gallery** (suggested working name; confirm or rename) |
| One-liner | A self-contained, file-backed PWA for securely documenting and reviewing a patient's wound-photo progress over time. |
| Target platform | Responsive web PWA, installable on desktop, tablet, and mobile; served by PHP. |
| Target users | **Primary assumption:** a clinician or authorized care-team member maintaining wound records. **Secondary assumption:** a demo evaluator reviewing longitudinal records. Patient self-service is not in the stated scope. |
| Success signal | An authorized user can reliably record and revisit every wound, update, scoped note, and angle photo online or from an explicitly synced offline copy, without lost, duplicated, stale, or misleading data. |
| MVP must-have | Demo login; seeded patient and data; progress-library CRUD; wound CRUD/state; date timeline and updates; three note scopes; secure upload/placeholder/photo metadata/reorder; responsive accessible UI. |
| Mandatory | File-only canonical storage; one self-contained `index.php`; authenticated media; CSRF and safe atomic file operations; installable opt-in offline PWA; complete patient sync; visible pending outbox; explicit conflict-aware replay; cache clearing on request/logout. |
| Later / optional | Drag-and-drop reordering, additional patient management, analytics, clinical decision support, remote collaboration, and production identity integration. These are not required by `PLAN.md`. |
| Constraints | No database, framework, Composer, CDN, external images, or remote service. No `localStorage`/`sessionStorage`. Application data remains server-canonical JSON plus separate image files. PHP sessions are authentication-only. |

### Decisions already specified by the source plan

- The domain hierarchy is `Patient → Progress Library → Longitudinal Wound → Date-specific Wound Update → Angle Photos`.
- The only seeded patient is non-identifying `Sample Patient`; patient CRUD is excluded.
- The demo credentials are `admin` / `password`, visibly labeled demo-only.
- A date-specific wound update can contain a note and zero photos; note-only updates still count as updates.
- Empty timeline days are virtual views and must not cause empty files or directories to be created.
- The server-side filesystem is authoritative. A device copy exists only after explicit consent and is always described as a replica.
- Online mutations are PHP POST actions with CSRF protection and redirect-after-POST. Offline changes remain visibly pending until accepted by PHP.
- Photos are original-size files, separate from metadata, and are served only through an authenticated media-ID route.

### Assumptions and suggested defaults requiring confirmation

1. **Clinical setting:** this is a single-user demonstration/recordkeeping tool, not a production EHR and not a multi-tenant system.
2. **Authorization:** every authenticated demo user can access the sole patient and all records; role-based access is deferred.
3. **Offline ownership:** one browser profile is treated as one device copy; logout clears it by default after warning about an unsynced outbox.
4. **Conflict policy:** revision mismatch pauses replay for explicit user resolution; the system never automatically merges or overwrites.
5. **Supported browsers:** current browsers with service worker, Cache Storage, and IndexedDB support; unsupported capability is explained without pretending offline availability.
6. **Photo limit:** 15 MB per JPEG, PNG, or WebP image, validated from server-read bytes. SVG is generated by the server only for placeholders and is not accepted as an upload.
7. **Retention/audit:** timestamped notes and created timestamps are records, but a full immutable audit log and regulatory compliance certification are out of scope.

## Requirements and Intelligence Grounding

### User needs

#### Use-based needs

- Start from a patient, choose the correct recovery library, and understand progress across dates.
- Record explicit wound updates quickly, including note-only updates and angle photos.
- See every active wound on every selected date so that “not updated” is never confused with “does not exist.”
- Manage notes at the library, day, and wound levels without losing scope.
- Continue core recordkeeping during an outage and deliberately reconcile pending changes later.

#### Usability-based needs

- Work on desktop, tablet, and phone with keyboard-accessible, labeled controls and strong focus/contrast.
- Keep long timelines navigable through month grouping or paging plus previous, next, and today/latest actions.
- Make empty, missing, loading, pending, conflicting, and saved states explicit in text, not color alone.
- Keep a previously synced gallery available immediately offline rather than blocking on a network request.

#### Meaning-based needs

- Feel calm and trustworthy without implying diagnosis or full EHR status.
- Preserve dignity through non-identifying demo data and clear privacy warnings around local photo copies.
- Give the user confidence that a pending offline action is not falsely represented as server-saved.

#### Social/status needs

- Support professional credibility through consistent terminology, predictable records, and visible integrity states.
- Fit familiar care-team workflows (patient → wound collection → date → wound update) without claiming regulated-system certification.

### Customer / market intelligence (hypotheses, not validated research)

#### ICP 1 — Small care team or clinic evaluator

- **Goals:** document repeat observations, compare dates, and avoid spreadsheet/shared-folder ambiguity.
- **Primary use cases:** capture wound updates, annotate photos, review progress, and work through unreliable connectivity.
- **Current alternatives:** camera rolls, shared folders, paper notes, spreadsheets, or broader EHR modules.
- **Differentiation:** a focused longitudinal model, explicit missing-update states, and user-controlled full offline copy in a dependency-free package.

#### ICP 2 — Home-health or field care worker

- **Goals:** capture complete records at the point of care despite intermittent service.
- **Primary use cases:** prepare a patient offline, review prior photos, stage updates, and explicitly sync on reconnect.
- **Current alternatives:** delayed transcription, generic note apps, or cloud tools that degrade without connectivity.
- **Differentiation:** opt-in original-photo sync, visible outbox, deterministic replay, and conflict protection.

#### ICP 3 — Product/demo reviewer

- **Goals:** verify a coherent wound-record workflow, storage integrity, accessibility, and offline resilience locally.
- **Primary use cases:** exercise seeded states and all CRUD/reorder/sync acceptance paths.
- **Current alternatives:** static prototypes or database-backed demos with hidden infrastructure.
- **Differentiation:** runnable from one PHP entry point with inspectable JSON/image storage and no third-party runtime dependencies.

These ICPs are planning suggestions. They require stakeholder or user validation before positioning, compliance, or go-to-market decisions.

## Required Planning Artifacts

### User flows

#### Onboarding / first run

1. Server starts and creates only the required writable storage structure and exact seed records.
2. User sees a compact login with demo credentials and the non-clinical disclaimer.
3. Invalid credentials return a clear error; valid credentials establish an authentication-only PHP session.
4. User lands on Patients and selects `Sample Patient`.
5. The patient view defaults to the most recent relevant date in a selected library and exposes the optional device-sync action.

#### Primary usage loop

1. Select patient → library → date.
2. Review date activity and every active wound, including muted missing updates.
3. Create or edit an explicit update; add a note, upload/create photos, label angles, caption, reorder, or delete.
4. PHP validates the mutation and revision, performs an atomic metadata/file update, then redirects with a success/error flash.
5. Refresh confirms canonical state, normalized photo order, and correct files.

#### Secondary flows

- Add/edit/delete a progress library and manage its longitudinal wounds.
- Add/edit/delete timestamped library, day, or wound notes from an exact-scope control.
- Navigate long timelines, including blank dates and partially updated dates.
- Opt into a full patient device copy after size/capability/privacy review; cancel, resume, update, or clear it.
- Stage supported mutations offline, review pending changes, and explicitly replay them online.
- Logout, clearing local clinical copies by default and warning if pending changes would be removed.

#### Error and edge-case flows

- Reject invalid login, CSRF, identifier, date, type, file size, decoded MIME, ownership, or reorder membership.
- Explain unwritable storage and preserve the prior valid JSON/files.
- Show “No wound updates recorded” for a wholly empty day; show “Not updated on this date” per missing wound; show “No photos added” for a note-only update.
- On insufficient browser storage, unsupported offline APIs, cancellation, or failed downloads, preserve existing cached data and mark the attempted copy incomplete.
- On revision conflict, stop replay at the conflict, retain the local operation, and offer reload-server or review/retry choices.
- On delete, confirm intent and remove only the resolved library/wound/photo target; compact photo ordering and leave no orphaned files.
- On connectivity changes, retain cached viewing and distinguish online, offline, syncing, pending, incomplete, and conflict states.

### State and persistence plan

| State class | Contents | Authority / lifetime |
| --- | --- | --- |
| Persisted business data | Patient snapshot; libraries; dates/updates; three note scopes; wounds; photo metadata; revisions | Atomic, locked server JSON is canonical. No blank-day artifacts. |
| Persisted media | Uploaded JPEG/PNG/WebP and generated black placeholder SVG files | Server filesystem hierarchy keyed only by validated/generated IDs; metadata stores filenames, never image bytes. |
| Persisted preferences/status | Per-patient sync manifest, last successful sync, completion/progress metadata, revision baseline | IndexedDB, only after explicit device sync; non-canonical and clearable. |
| Offline replica | App shell, patient snapshot, versioned authenticated media responses | Cache Storage, scoped to this app/patient; created only by explicit sync. |
| Offline pending work | Ordered mutation envelopes and selected image blobs | IndexedDB outbox; visibly pending until PHP accepts each operation. |
| Authentication | Logged-in flag and CSRF token | PHP session only; contains no clinical/application record data. |
| Temporary UI state | Selected tab/modal/form, progress display, transient validation, online indicator | Memory/DOM only; no `localStorage`, `sessionStorage`, or cookies. |

**Online behavior:** fetch structured state freshly when possible, mutate by validated POST, and refresh the canonical view. **Offline behavior:** render the last completed replica immediately, allow only supported staged actions, label them pending, and require user-triggered replay. A partial copy is never labeled available offline.

### Explicit UI states

- **First run:** demo credential callout, no clinical data before authentication, and seeded patient after sign-in.
- **Empty:** no updates on a day; wound not updated that day; updated wound with no photos; empty note scope; empty newly created library/wound list.
- **Loading:** initial network refresh, media loading, manifest calculation, sync preparation, and replay.
- **Error:** authentication, validation, storage, upload, media unavailable, sync download, quota, replay, and conflict messages with a recovery action.
- **Success/confirmation:** flash after server mutation; sync completed with timestamp; offline copy cleared; destructive confirmation before deletion.
- **Pending/incomplete:** pending-sync marker per staged change, outbox count, interrupted/partial copy, and retry/resume action.
- **Network:** `Online`, `Syncing`, `Offline — showing copy from <date/time>`, or `Pending changes` in persistent but unobtrusive status UI.
- **Edge cases:** long timeline, inactive wounds, custom library type, day note without wound activity, partial wound activity, reordered/deleted cached media, unsupported persistence, and stale revision.

## B. Epic Details

### E0. Planning & Decisions

- **Goal / user outcome:** stakeholders share a stable definition of the product's capabilities before implementation is sequenced.
- **Why this epic exists:** the offline/file-integrity requirements affect every domain action; premature coding would create incompatible interfaces.
- **Includes:** product brief, assumptions, needs, ICP hypotheses, flows, persistence, UI states, epic boundaries, coverage, and approval gate.
- **Dependencies:** `PLAN.md` and stakeholder confirmation.
- **Risks / unknowns:** intended operator, supported browser floor, regulatory expectations, and conflict UX have not been user-validated.
- **Out of scope:** implementation milestones, task estimates, code, and architecture-level function signatures.
- **Suggested order:** first; approve before any other epic is decomposed.

### E1. Trusted Access & Patient Entry

- **Goal / user outcome:** an authorized demo user can sign in, select the one patient, and sign out without leaking protected content.
- **Why this epic exists:** all records, manifests, and media require a clear authenticated boundary and entry journey.
- **Includes:** login error/success, visible demo credentials, authentication-only PHP session, CSRF identity, logout, Patients screen, patient selection, protected routes, app shell, disclaimer.
- **Dependencies:** approved E0; writable session environment.
- **Risks / unknowns:** demo credentials are intentionally unsuitable for production; offline launch must not bypass privacy semantics.
- **Out of scope:** patient CRUD, password recovery, roles, SSO, multi-user audit, production identity.
- **Suggested order:** first implementation capability; other server and offline endpoints inherit its access contract.

### E2. Progress Libraries & Timeline Navigation

- **Goal / user outcome:** users can manage distinct wound-progress collections and navigate from their starting date through today.
- **Why this epic exists:** libraries and their timeline establish the scope and revision boundary for all observations.
- **Includes:** seeded libraries, add/edit/delete, fixed/custom type, required start date, description, selection summaries, revisions, month/paged navigation, previous/next, today/latest, activity and day-note chip states.
- **Dependencies:** E1; shared safe JSON persistence conventions from E7.
- **Risks / unknowns:** default “most recent relevant” selection and behavior when a start date is edited need acceptance examples.
- **Out of scope:** type-specific data models, future dates, analytics, cross-library comparison.
- **Suggested order:** after E1, before wound/update and offline snapshot work.

### E3. Longitudinal Wounds & Daily Recording

- **Goal / user outcome:** users can maintain wound sites and truthfully distinguish explicit updates from missing observations on every date.
- **Why this epic exists:** this is the core recordkeeping loop and prevents absence of data from being misread as healing or deletion.
- **Includes:** seeded mixed-state dates, wound add/read/edit/deactivate/delete, safe cascade, all-active-wounds daily view, day-note shell, explicit update create/edit/delete, note-only update, empty/partial/missing text states.
- **Dependencies:** E2 hierarchy and timeline; E7 safe mutation primitives.
- **Risks / unknowns:** expected historical rendering after deactivation and whether wound deletion should ever be reversible require confirmation.
- **Out of scope:** clinical measurements, diagnosis, treatment recommendations, automated image interpretation.
- **Suggested order:** after E2; stabilize update identities before photo and outbox operations.

### E4. Scoped Notes & Context

- **Goal / user outcome:** users can add and retrieve context without confusing a library-wide note with a day or wound note.
- **Why this epic exists:** notes at three scopes are mandatory and their visible presence changes navigation and review behavior.
- **Includes:** multiple timestamped notes at library/day/wound scopes; add/edit/delete; exact-scope display; accent plus icon/text plus numeric accessible badge; note presence on selectors/cards/date chips.
- **Dependencies:** E2 and E3 scope IDs; E7 accessibility and atomic mutations.
- **Risks / unknowns:** author identity is unavailable in a single demo user model; editing timestamp policy should be confirmed later.
- **Out of scope:** rich text, attachments, mentions, comments, signatures, immutable audit trail.
- **Suggested order:** after base library/wound/date scopes; before freezing snapshot/outbox schemas.

### E5. Secure Angle-Photo Gallery

- **Goal / user outcome:** users can safely maintain an ordered, descriptive visual record for each explicit wound update.
- **Why this epic exists:** photos are the core evidence but create distinct validation, privacy, ordering, and filesystem-integrity risks.
- **Includes:** JPEG/PNG/WebP validation up to suggested 15 MB, generated IDs/names, separate metadata/files, black serial SVG placeholders, authenticated media lookup, angle/caption edit, delete, move controls, server-normalized order-prefixed filenames, orphan prevention, revision/cache version.
- **Dependencies:** E1 authentication, E3 update ownership, E7 filesystem safeguards; E4 schemas stable enough for patient snapshots.
- **Risks / unknowns:** browser upload memory/quota behavior, corrupt images, rename interruption, and large full-size sync cost.
- **Out of scope:** photo editing, thumbnails as canonical data, realistic generated wounds, image analysis, external object storage, drag-and-drop (optional later).
- **Suggested order:** after E3, with server operations settled before E6 caches and replays them.

### E6. User-Controlled Offline Continuity

- **Goal / user outcome:** users can knowingly carry a complete patient copy, view it without a network, stage changes, and reconcile without silent loss or overwrite.
- **Why this epic exists:** intermittent-connectivity continuity is mandatory, but local medical-photo storage needs explicit control and honest status.
- **Includes:** manifest/service worker/icons/offline route; authenticated sync manifest; full snapshot and original media; consent, estimate, privacy warning and persistence request; progress/cancel/resume; completed/incomplete status; cache-first synced photos and network-first/fallback structured data; update diff/removal; per-patient clear; offline navigation; IndexedDB outbox/blobs; pending overlays; explicit ordered replay; revisions/conflicts; temporary placeholders; quota handling; logout cleanup warning.
- **Dependencies:** stable E1–E5 identifiers, schemas, routes, revisions, and mutation semantics; E7 status/accessibility standards.
- **Risks / unknowns:** browser storage eviction, iOS/browser PWA differences, offline authentication model, replay dependency graphs, and concurrent server edits are the highest-complexity areas.
- **Out of scope:** automatic background reconciliation, silent last-write-wins, encrypted-at-rest claims, multi-device live collaboration, remote push.
- **Suggested order:** after online workflows and revision contracts are proven; introduce viewing/copy lifecycle before outbox/replay when milestones are later approved.

### E7. Record Trust, Safety & Inclusive Use

- **Goal / user outcome:** users can trust that records survive failures, destructive actions target only intended data, and every status/control is perceivable and operable.
- **Why this epic exists:** file storage, private imagery, and offline overlays make integrity and accessibility product outcomes, not cleanup tasks.
- **Includes:** atomic temporary-write/rename with locking; safe IDs/path containment; scoped recursive deletion; CSRF; server validation; redirect/flash; actionable writable-storage failures; semantic labels/alt text/focus/contrast/keyboard support; responsive layout; no-color-only meaning; calm design; non-diagnostic disclaimer; acceptance/integrity verification.
- **Dependencies:** applies to every epic and must be defined alongside E1, then exercised continuously.
- **Risks / unknowns:** crash-consistency boundaries, platform filesystem behavior, and full accessibility browser/device coverage.
- **Out of scope:** formal security certification, HIPAA/compliance attestation, penetration-test warranty, disaster-recovery service, clinical validation.
- **Suggested order:** establish guardrails with E1 and apply throughout; complete final cross-epic hardening only after capability implementation.

## Recommended Epic Implementation Order

After approval, the recommended capability order is **E1 → E2 → E3 → E4 → E5 → E6**, with **E7 applied continuously** rather than postponed. This order makes authenticated IDs, canonical data, revisions, and online mutations stable before an offline replica and replay protocol depend on them. This is epic sequencing only, not a milestone breakdown.
